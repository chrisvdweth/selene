Dataset Preparation¶

In this notebook, we will be using the CIFAR-10 dataset, a dataset of small color images commonly used to teach and benchmark image-classification methods. It contains 60,000 images, each 32 × 32 pixels with three color channels, divided among 10 classes: airplane, automobile, bird, cat, deer, dog, frog, horse, ship, and truck. The dataset is organized into 50,000 training images and 10,000 test images. Each image has one class label, and the class distribution is balanced, with 6,000 images per class overall.

CIFAR-10 was created by Alex Krizhevsky, Vinod Nair, and Geoffrey Hinton from larger images collected from the web and labeled through crowdsourcing. Its small size makes it popular in education: it needs relatively little storage and can be used for experiments without extensive computing resources. However, it is best suited to learning and comparing basic techniques. Its limited image resolution and dataset size are not enough to train state-of-the-art image classifiers, which typically require much larger datasets and substantially more computing resources.

Image Normalization¶

A very common preprocessing step when working with images for machine learning tasks is to normalize them before passing them to a model. Normalizing images by subtracting the training set's average value for each color channel centers the inputs around zero. This gives the CNN inputs on a more consistent scale and can make optimization easier: the model does not have to learn around a large, shared brightness or color offset, which can help gradients and training behave more steadily.

Without this centering, the model can still learn, but training may be less efficient or more sensitive to choices such as the learning rate and weight initialization. The channel means are typically calculated from the training data and then applied to the training, validation, and test images, so information from the held-out data does not influence preprocessing.

In the code cell below, we first compute the channel statistics (mean and standard deviation). Recall that raw_train is a CIFAR10 object containing the training images and their labels. Using torch.stack() and list comprehension to extract and combine all images tensors, we get single 4D tensors with the shape $(N, C, H, W)$: number of images ($N$), color channels ($C$), image height ($H$), and image width ($W$); for CIFAR-10, the shape is $(50000, 3, 32, 32)$. Using this tensor, we can now compute the channel statistics. The results each contain three values: one for red, one for green, and one for blue.

# Shape: (N, C, H, W)
images = torch.stack([image for image, _ in raw_train])

# One mean and standard deviation per channel, across all images and pixels
channel_mean = images.mean(dim=(0, 2, 3))
channel_std = images.std(dim=(0, 2, 3))

print("Mean:", channel_mean)
print("Std: ", channel_std)

With these channel statistics we can now normalize both the training and test images. torchvision makes it convenient to define image preprocessing as a sequence of transforms and apply it automatically whenever an image is retrieved from a dataset. transforms.Normalize standardizes each color channel by subtracting its mean and dividing by its standard deviation; transforms.Compose chains the steps together: each image is first converted to a tensor, then normalized using the training-set statistics. The transform is applied when an image is accessed via the CIFAR10 class, so you do not need to normalize and save a separate copy of every image. Although download=True is specified for convenience, torchvision checks the target folder first: because the dataset was downloaded there earlier, it will reuse the existing files rather than download them again.

Model Training & Evaluation¶

CNN Architecture¶

In the following, we consider the most basic architecture of a CNN model — that is (a) a series on convolutional layers for feature extraction and (b) a series of fully connected layers that eventually map the input to the $10$ output classes:

  • Feature extractor. CNNs typically stack multiple convolutional layers so the model can build increasingly useful image features. Earlier layers tend to respond to simple local patterns, such as edges, while later layers can combine those responses to recognize more complex patterns, such as textures, parts, or shapes. Each layer processes the feature maps produced by the previous one, allowing information from a wider region of the image to influence deeper representations. Together, these layers form a feature extraction module that turns raw pixel values into representations that are more useful for the classification task.

  • Classification head. The convolutional layers extract spatial features from the image, producing a set of feature maps that describe patterns detected in different locations. A classification head takes these learned features and uses them to predict which class the image belongs to. These layers combine information across the extracted features to produce class scores. Intermediate fully connected layers may learn useful combinations of features, often with nonlinear activation functions between them, while the final layer outputs one score, or logit, for each class.

The code cell contains the implementation of the CNN model in PyTorch. The class CnnClassifierCFIAR10 utilizes the utility class nn.Sequential to organize all layers into the feature extractor self.features and the classification head self.classifier. The feature extractor contains three convolutional layers that are quite similar in the sense that all three layers

  • Use a kernel size of $3\times 3$ (an integer value kernel_size implies a square kernels)
  • Use 1-pixel padding — together with $3\times 3$ kernels this means that the ouput shapes are the same as the input shapes
  • Are followed by a $\text{ReLU}$ activation function and a pooling layer with a window size of $2$ and a stride of $2$ (if stride=None, the same value as for stride is used); these parameters mean that the pooling layers halves the size of feature map in terms of their heights and width.

The main difference between the three convolutional layers is with respect to their number of kernels. The number of kernels in a convolutional layer is a design choice. Each kernel can learn to respond to a different feature, so more kernels let a layer represent a wider variety of patterns. The trade-off is greater memory use and computation. In practice, the number is chosen based on the task, input size, available resources, and experiments with model performance; there is no single best value. It is common for CNNs to use more channels in deeper layers, often as the feature maps become smaller through, e.g., pooling. A smaller spatial size can make it more affordable to increase the channel count while keeping computation manageable. This is a widely used design pattern, though architectures vary, and increasing the number of kernels is not required at every layer.

class CnnClassifierCFIAR10(nn.Module):
    
    def __init__(self, num_classes=10):
        super().__init__()

        self.features = nn.Sequential(

            # 1st convolutional layer: # 32 x 32 -> 32 x 32
            nn.Conv2d(3, 32, kernel_size=3, padding=1),
            nn.ReLU(),
            nn.MaxPool2d(kernel_size=2),  # 32 x 32 -> 16 x 16

            # 2nd convolutional layer: # 16 x 16 -> 16 x 16
            nn.Conv2d(32, 64, kernel_size=3, padding=1),
            nn.ReLU(),
            nn.MaxPool2d(kernel_size=2),  # 16 x 16 -> 8 x 8

            # 3rd convolutional layer: # 8 x 8 -> 8 x 8
            nn.Conv2d(64, 128, kernel_size=3, padding=1),
            nn.ReLU(),
            nn.MaxPool2d(kernel_size=2),  # 8 x 8 -> 4 x 4
        )

        self.classifier = nn.Sequential(
            nn.Flatten(),
            nn.Linear(128 * 4 * 4, 256),
            nn.ReLU(),
            nn.Dropout(0.5),
            nn.Linear(256, num_classes)
        )

    def forward(self, x):
        x = self.features(x)
        return self.classifier(x)

Auxiliary Methods¶

To make the model training more convenient and the code easier to read, we define a couple of auxiliary methods. The first, train_epoch trains the given model for a single epoch with respect to the given data loader (which typically will be the data loader containing the training data). Fundamentally, this method implements the most basic training loop that iterates over all batches in the data loader and performs the core steps:

  • Pass the inputs and labels to the model to get the model outputs
  • Compute the loss with respect to the given loss function (often called criterion, in practice)
  • Perform backpropagation and update the learnable parameters using the functionality provided by PyTorch

During these steps, the method keeps track of the total loss across all batches and returns that total loss at the end.

# training
def train_epoch(model, loader, optimizer, criterion):
    # Initialize epoch loss (cummulative loss fo all batchs)
    epoch_loss = 0.0
    # Use tqdm to get a nice progress bar
    with tqdm(total=len(loader)) as pbar:
        # Iterate over all batches
        for X_batch, y_batch in loader:
            # Move the batch to the correct device
            X_batch, y_batch = X_batch.to(DEVICE), y_batch.to(DEVICE)
            # Get model outputs as log probabiltiies
            log_probs = model(X_batch)
            # Calculate loss
            loss = criterion(log_probs, y_batch)
            ### Pytorch magic! ###
            optimizer.zero_grad()
            loss.backward()
            optimizer.step()
            # Keep track of overall epoch loss
            epoch_loss += loss.item()
            # Update progress bar
            pbar.update(1)
    # Return total loss across whole dataset
    return epoch_loss

Very similar to the method for training for a single epoch, the method evaluate() takes in a model and a data loader as arguments. Again, the model iterates over all batches of the data loader and passes the inputs (i.e., the images) to the model to get the predicted class labels. The method records all true and predicted class labels and returns both at lists; we can later use these lists to compute additional metrics to evaluate the performance of the model.

def evaluate(model, loader):
    # Define 2 lists holding all true labels and all predicted labels
    y_true, y_pred = [], []
    # Use tqdm to get a nice progress bar
    with tqdm(total=len(loader)) as pbar:
        # Iterate over all batches
        for X_batch, y_batch in loader:
            # Move the batch to the correct device
            X_batch, y_batch = X_batch.to(DEVICE), y_batch.to(DEVICE)
            # Get model outputs as log probabiltiies
            log_probs = model(X_batch)
            # Calculate predicted class labels based on largest log probability values
            y_batch_pred = torch.argmax(log_probs, dim=1)
            # Add the true labels and predicted labels for batch ot final lists
            y_true += list(y_batch.cpu())
            y_pred += list(y_batch_pred.cpu())
            # Update progress bar
            pbar.update(1)
    # Return all fround truth and predicted class labels
    return y_true, y_pred

Side note: In PyTorch, model.train() and model.eval() set the model's mode. We need to call model.train() before training so layers such as dropout and batch normalization behave as intended for training; we call model.eval() before validation or testing so dropout is disabled and batch normalization uses its learned running statistics. Alternatively, for evaluation, we can also use torch.no_grad() or torch.inference_mode() to avoid computing gradients and reduce memory use — we see later an example for that.

Evaluating the Result¶

Although the training loop prints the loss and the two F1 scores (for the training and validation) data after each epoch, it is typically very useful to also visualize the result in a single plot. For this, we provide the auxiliary method plot_training_results() as shown in the code cell below.

plot_training_results(results, legend=['Loss (normalized)', 'F1 (train)', 'F1 (val)'])

The result plot shows that the training is still decreasing, and the training F1 score is still increasing after $10$ epoch. However, we can also see that the validation F1 score more or less stopped improving after around Epochs $5\text{-}7$; this can different between different runs. This clear moving apart between the training and validation performance indicates that our model is already starting to overfit. Of course, to really make this statement — even for the exact same model architecture — would require a more elaborate evaluation, e.g., by training with different learning rates and/or different optimizers. However, we skip those steps here to keep the notebook simple.

So far, we have only seen the F1 score for the validation set — and since we do not perform cross-validation together with any hyperparameter tuning, the validation F1 score already gives a good estimation for the overall model performance. Still, for the sake of completeness, let's now also compute the F1 score with respect to the test data.

y_test_true, y_test_pred = evaluate(model, loader_test)

f1_test = f1_score(y_test_true, y_test_pred, average='macro')

print(f"F1 score for test set: {f1_test:.3f}")

F1 score for test set: 0.759

Unsurprisingly, the test F1 score is very similar to the one for the validation data.

The F1 score combines precision and recall into a single metric, making it a useful summary of a model's overall performance, especially when both false positives and false negatives matter. For a multiclass task, however, a single aggregate F1 score can hide how performance differs across classes. A model may classify some classes reliably while struggling with others, even if its overall score looks reasonable.

A confusion matrix helps reveal these differences by showing which classes the model predicts correctly and which it confuses with one another. Looking at the off-diagonal entries can highlight false positives, where images from one class are assigned to another, and false negatives, where examples of a class are missed. This makes it easier to identify which classes pose the greatest challenges for the model. We therefore provide the auxiliary methods plot_confusion_matrix() to get a better assessment for how well our trained model performs.

plot_confusion_matrix(y_test_true, y_test_pred, class_names)

As the confusion matrix shows, the model may most often confuse cats and dogs because CIFAR-10 images are small and low-resolution, so details that distinguish the animals (such as facial features, body shape, or fur patterns) can be hard to see. Their colors and poses can also look similar, especially when the animal occupies only a small part of the image or blends into the background. This is not very surprising: cats and dogs share many visual features — but also the other two animal classes "deer" and "horse" — and even people may find some tiny or unclear examples difficult to identify. The confusion suggests that the model has learned useful visual patterns, but those patterns are not always detailed enough to separate these similar classes reliably.

Inspecting the Model¶

Metrics such as the F1 score, together with a confusion matrix, show how well a model predicts and which classes it tends to confuse. But these results do not tell us what visual cues the model relies on. For example, a classifier might learn to associate a particular background, watermark, or image border with a class instead of focusing on the object itself. Such shortcuts can produce good results on familiar data but fail when those artifacts are absent or changed.

Investigating what a model has learned is less straightforward than calculating performance metrics. It may require interpreting internal activations or learned parameters, and those results can be difficult to understand. To keep the discussion accessible within this notebook, we will look at a simple example involving a single image to illustrate how we might begin to inspect the model's behavior.

To this end, we get an image from the first batch of the test data. By default, we choose the 2nd image showing a ship (more specifically, a yacht) as it is arguably one where it is easy to spot the correct class. However, you are encouraged to try different images and see how the choice of the images affects the following evaluation results.

for X_batch, y_batch in loader_test:
    image = X_batch[1]
    break

Before continuing, let's first have a look at the image itself. While we provide the auxiliary method show_image_from_array() for that, remember that all images have been normalized and we have changed their shape to align them with the expected inputs for PyTorch models. We therefore need to undo both these operations so that we can show the original image in its restored state.

image_unnormalized = image.permute(1,2,0)
image_unnormalized = image_unnormalized * channel_std + channel_mean
image_unnormalized = image_unnormalized.clamp(0, 1)

show_image_from_array(image_unnormalized, pixel_size=5)

To get a first look at what the model responds to in an image, we can inspect the activations after the first convolutional layer and its $\text{ReLU}$ activation. Each convolutional filter produces a feature map showing where its learned pattern is detected; $\text{ReLU}$ sets negative responses to zero, leaving stronger positive activations visible. Displaying these maps can reveal which regions of the image excite different filters and whether they respond to patterns such as edges, color contrasts, or simple textures. This gives only a partial view of what the model has learned. Early-layer activations show responses to one image, but they do not by themselves explain how the model combines features in deeper layers to make a class prediction. Still, they provide an accessible starting point for seeing whether the network responds to meaningful parts of the image or appears sensitive to unexpected regions or patterns.

In the code cell below, we first create an "artificial batch" for our single image so we can pass it the trained model. From the output of the model above, we know that the first two layers in model.features refer to the first convolutional layer and the subsequent $\text{ReLU}$ activation function. We therefore pass our image only through these two layer to get the activation we want to inspect. Since the the first convolutional layer uses $32$ kernel, we get $32$ feature maps we can plot.

with torch.no_grad():
    x = image.unsqueeze(0).to(DEVICE)  # (1, 3, 32, 32)
    # Example: activations after the first convolution and ReLU
    activations = model.features[:2](x).squeeze(0).cpu()  # (channels, height, width)

fig, axes = plt.subplots(4, 8, figsize=(12, 6))
for i, ax in enumerate(axes.flat):
    ax.imshow(activations[i], cmap="viridis")
    ax.set_title(f"Map {i}")
    ax.axis("off")
plt.tight_layout()
plt.show()

For the yacht image, the strongest activations in some first-layer feature maps may appear along horizontal edges. This is expected because the image contains several strong horizontal lines, including the rows of windows and the boundary between the deck and the hull. These edges create sharp local changes in color and brightness that filters tuned to horizontal patterns can detect. Keep in mind, however, that the filters are not recognizing the yacht as a complete object; they respond to simple visual patterns in particular regions. Later layers can combine these edge responses with other features to build more complex representations.

Feature maps from later convolutional layers are harder to interpret because they respond to combinations of patterns detected by earlier layers. Instead of activating for a simple feature such as a horizontal edge, a deeper filter may respond to a more complex arrangement of edges, textures, and shapes. Its activations can also depend on a larger region of the image, making the pattern less obvious when viewed in isolation. As a result, later feature maps often look abstract or fragmented rather than like recognizable parts of an object. Their meaning is specific to the model and the input image, and generally cannot be identified just by looking at one map. They still carry useful information for classification, but interpreting them usually requires more involved methods.

Summary¶

In this notebook, we went through the basic workflow for training a CNN-based image classifier using CIFAR-10. We inspected example images and class distributions, prepared and normalized the data, and split the training set into training and validation subsets while keeping the test set for final evaluation. We then built a simple CNN, configured its optimizer and loss function, and trained and evaluated the model. The notebook's purpose was educational, so it used a small, straightforward model and dataset to make the main steps easier to follow. The results also showed that image classification can be challenging: CIFAR-10's low-resolution images can be ambiguous, and some classes, such as cats and dogs, are easy for the model to confuse.

The same overall workflow applies to larger datasets and more complex models, but each step may require more care. Data preparation, model design, training strategies, and evaluation can become more involved, and training may demand substantially more time, storage, and computing resources. Treat this notebook as a starting point and a blueprint for more practical image-classification projects. It provides a foundation you can build on by experimenting with stronger architectures, richer preprocessing, and more advanced training and evaluation methods.
